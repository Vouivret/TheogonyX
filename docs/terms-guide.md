# 用語ガイド（やさしい説明）

ゲームと仕様書に出てくる言葉を、分野ごとに説明する。**用語の原本は [用語集](domain/glossary.md)** で、ここはそれを読み進めるための手引きである（意味が食い違ったときは用語集が正）。

「状態」の列は次のとおり。

- **ある**: 今のゲームに作ってある。
- **構想**: 仕様書やロードマップに案があるが、まだ作っていない。
- **決定**: 仕様として決めたが、実装は途中。

## 1. ゲームの大きな流れ

神（プレイヤー）は、世界に直接さわれない。予言者が見た夢を書き換え、ドグマ（教義）を世界に放つ。すると数十〜数百年のあいだに、人間と環境が思いもよらない形に変わっていく。それを眺めて楽しむ「アクアリウム」のようなゲームである。

```
夢（予言者）→ 改ざん（神）→ 神託を下す → ドグマが生まれる → 年が進む → 環境と人間が変わる
```

| 用語 | やさしい説明 | 状態 |
| :--- | :--- | :--- |
| 神 | プレイヤー。直接は世界を変えられず、夢を書き換えて間接的に介入する | ある |
| 予言者 | 夢を見て、神のお告げ（神託）を人々に伝える人間。画面の中央にいる | ある |
| 星 | 舞台になる世界。環境の数値と 16 の地域と地層を持ち、崩壊することがある | ある |
| 年 | 時間の単位。ゲームは年を 1 つずつ進める。数百年を一気に跳ぶこともある | ある |
| アクアリウム（間接操作） | 神は住人や建物の数値を直接変えられない。「一滴のインク」を落とし、結果を観察する、というこのゲームの考え方 | ある（方針） |

## 2. 夢と神託（ゲームの中心）

> 2026-10-14 に、神託の作り方を「夢のコマを書き換える」から「手札のルーンを 2 枚選ぶ」に変えた（[神託の作り方](domain/oracle-pair.md)）。夢・夢ノード・改ざんは廃止した（下の表の「夢」「夢ノード」「改ざん」の行は、経緯のために残している）。

| 用語 | やさしい説明 | 状態 |
| :--- | :--- | :--- |
| 夢 | （廃止）予言者が見ていた、記号が 3 つ並んだもの。神託を手札のルーンの組で作る形に変えたので無くなった | 廃止 |
| 夢ノード（コマ） | （廃止）夢の 1 コマ。夢と一緒に廃止した | 廃止 |
| 記号（シンボル） | 夢を作る意味の単位。今は木・恵みの雨・血・聖なる火の 4 つ | ある |
| 感情の極性 | 記号が呼ぶ気持ち。−1.0（恐怖）〜 +1.0（歓喜）。ドグマの種類を決める | ある |
| 衝撃度 | 隣り合う 2 コマの印象の強さ。いちばん強いペアがドグマになる | ある |
| 概念カード（概念ルーン） | 神が手札に持つカード。2 枚を選んで神託にする（1 枚目がドグマの対象） | ある |
| 改ざん | （廃止）夢のコマを手札のカードと入れ替えること。夢と一緒に廃止した | 廃止 |
| 神託を下す | 手札の 2 枚のルーンからドグマを作り、世界に放つこと。神威を使う | ある |
| ドグマ | 夢から生まれた教義。「何を」（記号）と「どうする」（種別）と「強さ」を持ち、毎年環境に効く | ある |
| ドグマの種別 | 禁忌（触れるな）・崇拝（あがめよ）・破壊（打ち壊せ）の 3 つ。極性の和で決まる | ある |
| 予言者の依頼（祈り） | 水や森林が足りなくなったとき、予言者が吹き出しで出す頼みごと | ある |
| 問解 | 人間から神への問い合わせに、カードで答える案。依頼がその役を担っているので、作るか未定 | 構想 |

## 11. 仕組みと開発の用語

| 用語 | やさしい説明 |
| :--- | :--- |
| コア（TheogonyX.Core） | ゲームの計算をする部分。Godot に依存せず、同じ入力から同じ結果になる |
| ホスト | 計算と描画を行う PC 側のゲーム（Godot） |
| コンパニオン | スマホのブラウザで開く神託の操作画面。WebSocket でホストにつながる |
| ペアリング | スマホをホストにつなぐこと。QR コードのワンタイムトークンで認証する |
| Tick | 計算の 1 回。このゲームでは 1 年 |
| 決定性 | 同じシード・同じ操作から、同じ結果になること |
| シード | 乱数の元の値。同じシードなら同じ並びが再現される |
| PRNG | シードから決まる疑似乱数 |
| セーブデータ / saveVersion | 保存の形式と、その版の番号。形を変えると上がり、古いセーブは読めなくなる |
| 受け入れ条件（AC） | 仕様書に書く、「この前提で操作したらこうなる」という確かめる条件 |
| テスト観点（TS） | テスト仕様書の 1 行。どの受け入れ条件を、どう確かめるか |
| `TODO(AI_UNSURE)` | AI が決められず仮に置いた値や規則の印。人間が決め直す |
| ADR | 設計の判断と理由を残す文書 |
| status: draft / approved / as-is | 仕様書の状態。下書き / 人間が承認 / コードから起こしたもの |
| BREAKING CHANGE | セーブの互換性を壊す変更。コミットの件名に `!` を付ける |
