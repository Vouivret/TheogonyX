# AI時代の開発ハンドブック（チーム向け）

> **配置先**: `docs/DEV_HANDBOOK.md`
> 人間向けに、ルールの背景・意図と、人間が担う観点をまとめる。AIが守る具体的な制約（数値の目安、禁止事項、ファイルの置き場所）は `.agent/` にだけ書き、ここには繰り返さない。

## 1. テスト戦略の考え方

AIはモックを多用した単体テストを大量に生成しがちである。こうしたテストは実装の内部構造に依存するので、リファクタリングのたびに壊れ、そのくせ実際の不具合は見逃す。

そこで、検証の重心を結合テストに置く。この形は一般に「テスティングトロフィー」と呼ばれる。

- **型・静的解析**を土台にする。型で保証できることはテストを書かずに型に任せる。
- **結合テスト**を中心にする。1ケースで、実際の利用に近い経路を大きく検証する。このゲームでは、Godot から切り離したシミュレーションのコアを、固定シードで「夢の改ざん → ドグマ生成 → 時代跳躍 → 世界の状態」まで通しで検証するテストがこれにあたる。
- **単体テスト**は、外部依存の無い計算や状態遷移の境界値に絞る。
- **E2E**にあたる見た目・操作感・コンパニオンとの接続は、Godot を起動する自動テストの保守コストが高いので、テスト仕様書の手動テストとして実機で確かめる。

層ごとの具体的な方針は `.agent/rules/testing.md` を参照。

### 1.1 テスト仕様書を置く理由と、置きすぎない理由
自動テストのコードは、それ自体が実行できる仕様書である。テスト仕様書に同じ手順を書くと二重管理になり、どちらかが必ず古くなる。そのためテスト仕様書には、コードには書けないことだけを置く。

- **観点**: 何を確かめるか、なぜ必要か。コードを読んでも分からない意図。
- **手動テスト**: 目視、実機、外部サービスとの連携など、自動化できないもの。
- **つながり**: 観点がどのテストで確かめられているか。

仕様書と実施記録の関係は、アーキテクチャ概要とADRの関係と同じである。テスト仕様書は常に今の姿へ書き換え、手動テストの実施記録は追記だけにする。

AIに頼むときに最も警戒すべきなのは、今のコードの挙動を読み取ってテスト仕様書を書かせることである。バグがそのまま「期待結果」として固定される。テスト仕様書は、必ず仕様書（受け入れ条件）から作らせる。

### 1.2 CIでのずれの検出
テスト仕様書で種別が「自動」になっているIDが、テストコードに存在するかをCIでチェックする。逆に、IDの付いたテストが仕様書に無い場合も検出する。こうすると、片方だけ消えたり変わったりしたときに気付ける。

このチェックはCI専用にせず、README の「確認」コマンドに含める。AIが手元で同じチェックを実行できれば、IDの付け忘れをPRを出す前に自分で直せる。中身は、仕様書の表からIDを抜き出し、テストコードを検索して突き合わせるだけの短いスクリプトで足りる。テストのIDの書き方（テスト名かタグか）が言語ごとに違うので、スクリプトはプロジェクトごとに用意する。

## 2. 推奨する開発パターン

プロジェクトの性質に合わせて取捨選択してよい。共通の考え方は、**人間が「何を・なぜ」を決め、AIが「どう書くか」を担う**ことである。

| 工程 | 人間が決めること | AIに任せること | 例（このゲームの場合） |
| :--- | :--- | :--- | :--- |
| 1. ドメインの整理 | ゲームの概念・用語・境界 | モデルのコード化 | 用語集から `Symbol`・`Dogma`・`WorldState` を作る |
| 2. インターフェースの定義 | コアと Godot、ホストとコンパニオンの契約 | 契約から型を作る | `docs/protocol/messages.md` から C# のメッセージ型を作る |
| 3. コアロジックの実装 | ゲームのルールと調整値の決め方（テストとして書く） | テストを満たす実装 | 夢の解釈・時代跳躍を TDD で作る |
| 4. 機能の組み上げ | 画面・演出の仕様、使う部品 | シーンとスクリプトの実装 | UI テーマと共通シーンを渡して実装させる |

ライブラリやCLIの場合は、2の「契約」が公開APIやコマンドの仕様に置き換わる。

### 2.1 コードの前に処理の流れを確認する
複雑な処理をAIにいきなり書かせると、全体の設計が固まらないまま実装が進み、途中で破綻することがある。数百行のコードを読んで方向違いに気付くより、十数行の箇条書きで気付くほうがずっと安い。そこで、条件に当たる処理（`.agent/rules/project.md` 2.3）では、まず処理の流れを日本語の箇条書きで出させ、人間が確認してから実装に進ませる。確認の観点は、分岐の漏れ、例外時の扱い、既存データへの影響である。

## 3. AIへの依頼の仕方

- **タスクを小さく切る**: 変更範囲が大きいと、AIの見落としもレビューの見落としも増える。
- **渡すコンテキストを絞る**: 次に絞る。
  1. 該当機能の仕様
  2. 関連する型定義
  3. 修正対象のコード
  4. 必要に応じて ADR
  
  無関係なファイルを渡すと、AIはそれも変えようとする。
- **決まっていないことは「未決」と明示する**: AIは曖昧な部分を推測で埋めて、それらしく完成させてしまう。
- **設計と実装でセッションを分ける**: plan を作り終えたら、会話（セッション）をリセットしてから実装を頼む。同じ会話のまま進めると、AIは検討の途中で捨てた案に引きずられる。新しいセッションでは「実装を開始して」のように頼み、plan ファイルだけを仕様として読ませる。plan に書かれていないことはAIに伝わらないので、決めたことはすべて plan に残す。

## 4. CIとレビュー

### 4.1 CIに任せること
人間が目で確認しなくてよいものは、すべてCIで自動的にブロックする。
- 構文エラー、型の不整合、フォーマット違反、ビルドやテストの失敗
- 自動生成物と生成元の不一致（CI上で再生成し、差分が出たら失敗にする）
- テスト仕様書のIDとテストコードの不一致（1.2 を参照）
- 依存関係の既知の脆弱性（例: `npm audit`、`dotnet list package --vulnerable`、GitHub の Dependabot alerts）
- 秘密情報のコミット（例: GitHub の secret scanning、gitleaks）
- 多言語リソースのキーの欠け（対応言語のどれかにだけ無いキー）
- コミットメッセージの形式（Conventional Commits）
- 初期設定の未記入（`TODO(SETUP)`）。ひな形から始めたプロジェクトで、運用に必要な項目が空のまま使われるのを防ぐ
- 差分に残った `TODO(AI_UNSURE)`（AIが確認を待てずに仮置きした箇所。人間が判断して解消するまでマージしない）

### 4.2 人間が見ること
- ビジネスロジックが妥当か
- セキュリティ上のリスクが無いか
- 設計が保守しやすいか
- **フェーズに合った厳しさか**: 現在のフェーズは `.agent/rules/project.md` に書いてある。Phase 1 なら網羅的な異常系は問わないが、「どのフェーズでも省略しないこと」は必ず見る。
- **AIにレビューさせる場合**: `.agent/skills/review-pr.md` の観点で確認させる。AIのレビューは人間のレビューの代わりではなく、人間が見る前に機械的に確かめられることを潰しておくためのものである。
- **テストが仕様を検証しているか**: AIが書いたテストは、何も検証していないことがある。テストを書き換えたり、テスト専用の分岐を入れたりして「通した」ことにしていないかも確認する。

### 4.2.1 セルフレビューの実行記録
`/code-review` と `/ponytail-review` を実行すると、Claude Code のフック（`.claude/settings.json` と `.claude/hooks/log-review.sh`）が、日時・ブランチ・コミットを `.git/ai-review-log.jsonl` に記録する。PRを作るときにAIがこの記録をPRの「セルフレビュー」欄に転記し、記録が無ければ「未実行」と書く。AIの記憶に頼らないので、セッションを分けても、会話が要約されても記録は残る。「その後のコミット数」を見れば、レビューのあとにコードが変わったかも分かる。

限界もある。
- 記録は各自の手元にあり、本人なら書き換えられる。実行したことの記録であって、証明ではない。証明が必要なら、PRを作ったときにCIでレビューを実行する。
- Claude Code 以外のツールで行ったレビューは記録されない。
- `.agent/skills/review-pr.md` は手順書でありコマンドではないので、記録の対象外である。

### 4.3 PRを小さく保つ理由
AIは短時間で大量のコードを出せるが、人間のレビュー能力は変わらない。大きなPRは、読まれずに承認されやすい。

目安として、1PRの変更行数は300行以内にする。自動生成コード、lockfile、スナップショット、機械的な一括リネームは行数に数えない。超える場合は、PRの説明に分割できなかった理由を書く。

## 5. 仕様書と文書のつながり

### 5.1 文書の全体像
文書の置き場所と、AIが守ることの一覧は `.agent/rules/project.md` の4章にある。仕様書・テスト仕様書・アーキテクチャ概要は今の姿に書き換え、ADR・手動テストの実施記録・障害の振り返り・CHANGELOGは追記だけにする。

IDでつなぐ。

```
仕様書の受け入れ条件（AC-login-001）
  → テスト仕様書の観点（TS-login-003。確かめる AC を書く）
    → テストコード（テスト名に TS-login-003）
```

テスト仕様書の「受け入れ条件」列を見れば、まだテストで確かめていない受け入れ条件を洗い出せる。

### 5.2 図は Mermaid で書く
処理の順序やデータの関係は、文章だけで書くと抜け漏れが起きやすい（状態遷移は表で書く。5.2.1）。Mermaid の図はテキストなので、AIが読み書きでき、差分もレビューできる。画像の図は、AIが読めないうえに、古くなっても気付けない。

ただし、受け入れ条件は図にしない。テスト仕様書とIDでつなぐ単位なので、表のまま保つ。

### 5.2.1 状態遷移は表で書く
状態遷移を文章や図だけで書くと、「この状態でこの操作をしたらどうなるか」の組み合わせに抜けが出る。行に状態、列にきっかけを並べた表にしてすべてのマスを埋めれば、抜けは空欄として目に見える。実装も同じ形の表（配列や Map）で持たせると、仕様書との照合が1対1でできる。

### 5.3 用語集を置く理由
AIは、用語がぶれると同じ概念に別の名前のクラスや変数を作る。用語集で「この概念はコード上この名前」と決めておくと、命名が揃う。DDDでいうユビキタス言語にあたる。

### 5.4 `as-is` の仕様書
長期保守では、仕様書の無い既存機能が必ず出てくる。人間が先に仕様を書くまで手を付けられないのでは回らないので、AIにコードから現状を起こさせてよい。

ただし、コードから起こした記述には、不具合が「仕様」として紛れ込む。そのため状態を `as-is`（未確認）として区別し、人間が確認して `approved` にするまでは、テストの期待結果の根拠にしない。意図か不具合か判断できない挙動は「未決」に書かせ、確認の際に優先して見る。

## 6. 決定の記録: plan と ADR

### 6.1 なぜ2種類に分けるのか
plan ファイルは、チケットの仕様を書いたものである。実装中に上書きされ、チケットが閉じると読まれなくなる。決定の理由を plan だけに残すと、チケットをまたいだ「なぜこうなっているのか」を後から追えなくなる。

そこで、チケットを越えて効く決定だけをADRに格上げし、書き換えずに残す。チケットの中で閉じる判断は plan や PR の説明に置いたままにし、ADRの本数を抑える。

完了した plan は、完了のPRの中で `plan/archive/` へ移す。`plan/` の直下に残り続けると、AIが古い仕様を読み込んで、すでに変わった前提でコードを書いてしまう。削除ではなくアーカイブにするのは、当時の検討内容を後から追えるようにするためである。

### 6.2 長期保守でADRが増えても困らないようにする
10年保守をすると、ADRは数百本になりうる。本数そのものは問題ではない。問題になるのは、どれが今も有効か分からなくなることと、目当ての1本が見つからないことである。そこで次のように運用する。

- **入口を1つにする**: 普段読むのはアーキテクチャ概要（`docs/architecture.md`）だけにする。概要は常に現在の姿へ書き換え、各項目から根拠のADRへリンクする。ADRは「なぜ？」と思ったときに引く記録として扱う。
- **状態で絞り込む**: ADRの `status` で、今有効なもの（`accepted`）だけを抜き出せるようにする。分類はディレクトリではなく `area` タグで行う（領域をまたぐ決定の置き場所に困らないため）。
- **年1回棚卸しをする**: `accepted` のADRのうち、実態と合わなくなったものを `deprecated` にする。削除はしない。候補の洗い出しはAIに任せてよい。

### 6.3 ADRのひな形
ひな形は `docs/adr/0000-template.md` にある。AIも人間も、このファイルをコピーしてADRを書く。1本は1ページに収める。

各節の意図:
- **背景**: 決定が必要になった理由。後から読む人が、当時の制約を知るためのもの。
- **検討した他の案**: 同じ議論を蒸し返さないためのもの。採用しなかった理由とセットで書く。
- **結果**: 何を諦めたかと、再評価すべき条件。棚卸しのときの判断材料になる。

## 7. 非機能要件と依存関係の保守

### 7.1 非機能要件を1か所に置く理由
仕様書は機能ごとに分かれているので、「全体で応答2秒以内」「対応ブラウザ」のような横断的な要件の置き場所が無い。置き場所が無いと、要件は人の記憶の中にしか残らず、AIはそれを知る手段が無い。そこで `docs/nfr.md` に集め、AIには影響しうる変更のたびに確認させる。目標値を決めるのは人間で、AIには変えさせない。

### 7.2 10年保守での依存関係
10年のあいだに、ランタイムやフレームワークのメジャーバージョンは何度も変わり、サポート期限も切れる。放置すると、ある日まとめて上げることになり、大きな手戻りになる。

- **小さく、頻繁に上げる**: Dependabot や Renovate で更新PRを自動で作らせ、1つずつ取り込む。
- **期限を見える場所に置く**: `docs/nfr.md` の「対応環境とサポート期限」に、使っているランタイム・フレームワーク・OSのサポート期限を書く。
- **期限切れを機械で知らせる**: CIを定期実行（例: 月1回）し、`docs/nfr.md` の「サポート期限」列を読んで、1年以内に切れるものがあれば Issue を作る。期限の日付そのものも、公開されているデータ（例: endoflife.date のAPI）から取得すれば、表の書き忘れを防げる。Dependabot や Renovate はパッケージの新しいバージョンを知らせる仕組みで、ランタイムやOSのサポート期限は知らせてくれないので、別に用意する。
- **年1回見直す**: ADRの棚卸しと同じタイミングで、サポート期限が1年以内に切れるものの移行計画を立てる。
- **脆弱性はCIで止める**（4.1）。

## 8. 開発の流れ

### 8.1 ブランチとコミット
`main` から作業ブランチを切ってPRで戻す、単純な流れ（GitHub Flow）を基本にする。リリースブランチが必要になるのは、複数のバージョンを並行して保守する場合だけである。

コミットメッセージを Conventional Commits の形式に揃えておくと、種別（`feat`/`fix`/破壊的変更）からバージョン番号の上げ方を判断でき、CHANGELOGの下書きも自動で作れる。

### 8.2 Issue と PR
- Issue のひな形で、受け入れ条件（または仕様書へのリンク）を書く欄を必須にする。受け入れ条件の無い Issue は着手しない。AIに渡すときに「何ができたら完成か」が決まっていないと、AIは推測で埋める。
- PR のひな形には、Issue・仕様書の受け入れ条件・テスト仕様書の観点へのリンク欄を設ける。これで、文書のつながり（5.1）が日々の作業に組み込まれる。

### 8.3 開発環境
新しいメンバーが初日に動かせることを目標にする。README に、前提ツール・セットアップ・起動・テストの手順を、コピーして実行できる形で書く。

ビルド・lint・テストは、`npm run check` や `make check` のような1つのコマンドにまとめる。AIは毎回このコマンドで確認するので、確認のしかたがぶれず、失敗したときの自己修正も安定する。可能なら devcontainer で環境を固定する。人間だけでなくAIも、READMEの手順でビルドやテストを実行する。

## 9. リリースと障害対応

### 9.1 リリース
バージョン番号は Semantic Versioning（`メジャー.マイナー.パッチ`）で付ける。CHANGELOG は普段からAIに `Unreleased` へ追記させ、リリース時に人間がバージョン番号を付けて確定させる。リリース・デプロイ・ロールバックの手順は `docs/operations.md` に書く。ロールバックは、実際に一度試して手順が正しいことを確かめておく。

### 9.2 障害対応と振り返り
障害の対応手順（誰に連絡し、何を確認し、どう戻すか）は `docs/operations.md` に書く。収束したら `docs/postmortem/` に振り返りを書く。

振り返りは、誰のミスかではなく、なぜ仕組みで防げなかったかを書く（ブレームレス）。個人を責めると、次から事実が報告されなくなる。再発防止策は、AIのルール（`.agent/`）、CIのチェック、テスト仕様書の観点のどれかに落とし込む。そうすれば、次の障害はAIの作業の段階で防げる。振り返りを書いたら、`.agent/skills/analyze-postmortem.md` でAIに落とし込み先と変更案を出させ、採用するものを人間が選んでPRで反映する。

## 10. 多言語対応
多言語対応は、後から入れるほど高くつく。文字列がコードに散らばったあとでは、全画面を洗い直すことになる。最初は1言語だけでも、文字列をリソースファイルに置く作りにしておく。

- 対応言語は `docs/nfr.md` に書く。
- 訳語のぶれを防ぐため、用語集に各言語の表記を持たせる。
- 翻訳の品質は人間（できれば母語話者）が確認する。AIの翻訳は下訳として使う。

## 11. AIの利用ポリシー
どの情報をどのAIサービスに渡してよいかは、技術ではなく会社として決めることである。`docs/AI_USAGE_POLICY.md` は枠だけ用意してあるので、社内の情報セキュリティ規定に合わせて中身を埋める。埋まるまでは、社外秘の情報を外部サービスに渡さない運用にする。

## 12. ルールの運用

### 12.0 ルールの3層構成
AIに毎回すべてのルールを読ませると、コンテキストを圧迫し、個々のルールへの注意も薄れる。そこでルールを3層に分ける。

| 層 | 置き場所 | 読まれるとき |
| :--- | :--- | :--- |
| 共通ルール | `.agent/rules/project.md` | 毎回（`CLAUDE.md` から全文を取り込む） |
| 下位ルール | `.agent/rules/*.md`（C#、Godot、テスト、画面、通信、セーブデータ） | そのファイルを編集するとき（`project.md` の表で振り分ける） |
| スキル | `.agent/skills/*.md` | その作業をするとき（仕様書を書く、PRを締めくくる、など） |

新しいルールを足すときは、まず「全作業に共通か」を考える。特定のファイルを編集するときだけ必要なら下位ルールへ、特定の作業の手順ならスキルへ置く。`project.md` は200行以内を目安に保つ。

### 12.1 スキルを貯める
AIへの上手な頼み方を見つけたら、`.agent/skills/_template.md` をコピーしてスキルにし、PRで共有する。スキルには、入力・読むファイル・手順・出力の形を決めて書く。毎回のプロンプトの書き方に頼らず、誰が頼んでも同じ品質で作業が進むようにするためである。

### 12.2 AIに読ませないファイル
ロックファイル・自動生成コード・ビルド成果物・バイナリをAIが読むと、コンテキストを使い切り、回答の精度も落ちる。読まないファイルは `.agent/rules/project.md` の 2.2 にルールとして書いてある。

ルールだけでは確実ではないので、使っているツールの機能でも止める。ツールに共通の仕組みは無く（`.aiignore` という名前のファイルを置いても、読むツールが無ければ効かない）、ツールごとに設定する。

- Claude Code: `.claude/settings.json` の `permissions.deny` に `Read(./.godot/**)` のように書く（設定済み）。
- Cursor: `.cursorignore` に書く。
- GitHub Copilot: 組織やリポジトリの設定の「コンテンツの除外」で指定する。

ロックファイルは、依存関係の更新を調べるときに中身を見る必要があるので、ツールで完全には止めない。ルールで「検索で該当箇所だけを見る」に留める。

### 12.3 ルールを各ツールに届ける
ルールの原本は `.agent/rules/project.md` の1つだけにする。ツールごとに手で書き写すと、必ずどれかが古くなる。

- **取り込みができるツール**は、取り込みを使う。Claude Code は `CLAUDE.md` に `@.agent/rules/project.md` と書くと、全文が毎回読み込まれる。「このファイルを読め」というポインタと違い、AIが読み飛ばす余地が無い。
- **取り込みができないツール**には、原本をコピーしたファイルを自動で生成する（ひな形では `scripts/sync-agent-rules.sh` が `.github/copilot-instructions.md` を生成し、`.github/workflows/agent-rules.yml` が一致を確認する）。生成スクリプトは `README.md` の「確認」コマンドに含め、CIでは「生成し直して差分が出たら失敗」にする。Gitフック（husky など）だけに任せると、フックを入れていない人や `--no-verify` で簡単に抜けてしまうので、最終的な確認はCIで行う。
- ツールのルールファイルの形式は変わりやすい（例: Cursor は `.cursorrules` から `.cursor/rules/*.mdc` に移行した）。生成先は、各ツールの最新のドキュメントで確認する。

### 12.4 Web版のAIに相談するとき
ブラウザのAIに相談するときも、ルールと関連する仕様書を渡す。手で毎回コピーすると渡し忘れるので、リポジトリの一部を1つのファイルにまとめるツール（例: Repomix）を設定しておく。

ただし、これはコードを社外のサービスに渡す行為そのものである。`docs/AI_USAGE_POLICY.md` で、そのサービスに社内情報を渡してよいと決まっている場合だけ使う。まとめる対象から、秘密情報を含むファイル（`.env` など）は必ず除外する。

### 12.5 重複実装を防ぐ
AIは既存の部品を見落とすと、同じ働きの関数やコンポーネントを新しく作る。対策は、作る前に検索させること（`.agent/rules/project.md` 2.2）と、共通部品の置き場所を `docs/architecture.md` に書いておくことである。

全ファイルの一覧と説明を自動生成した「地図」を作る方法もある。ただし、大きなリポジトリでは地図そのものが巨大になり、毎回読ませるとコンテキストを圧迫する。作る場合も、まとめて読ませるのではなく、検索の対象として使う。

### 12.6 中核の処理を作り直すとき
AIは既存のコードを一度に丸ごと書き換えがちで、中核の処理でこれをやると影響が読みきれない。新しい実装を追加して切り替え可能にし、確認してから旧実装を消す、という段階的な移行（ストラングラーパターン）で進める。

ただし、切り替えの仕組み（フィーチャーフラグなど）は、残り続けると分岐が増えて保守の負担になる。旧実装の削除まで終えて完了とし、削除の予定は最初のPRの時点で Issue にしておく。小さな変更にまでこの手順を使う必要は無い。

### 12.7 機械的な変更を安全に通す
リネームや型の置き換えのような機械的な変更を、AIに手で書き換えさせると、ついでにロジックを少し変えてしまう事故が起きる。対策は次の3つ。

- **ツールでやらせる**: IDEのリファクタリング機能やコード変換ツール（codemod）は、機械的に正しく書き換える。AIにはツールを実行させ、手では書かせない。
- **PRを分ける**: 機械的な変更と振る舞いの変更を同じPRに混ぜない。機械的な変更のPRは、テストを1行も変えずに全部通ることが、ロジックが変わっていないことの確認になる。
- **差分を構文で見る**: difftastic のような構文を理解する差分ツールを使うと、インデントや改行だけの変化が消え、本当に変わった箇所だけが見える。ただし「差分がゼロ」を自動で保証する仕組みにはならない（リネームは構文上も変更である）ので、レビューを助ける道具として使う。

### 12.8 運用の決まり

- AIからのルール変更の提案は、PRとしてレビューしてから取り込む。
- ルールは増えすぎると守られなくなる。定期的に棚卸しをして、使われていないルールや重複したルールを削除する。
- フェーズの切り替えは、`.agent/rules/project.md` のフェーズ表記を人間が更新して行う。
