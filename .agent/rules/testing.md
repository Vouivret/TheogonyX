# テストコードのルール

> `.agent/rules/project.md` の下位ルール。矛盾した場合は `project.md` を優先する。
> 対象: テストコード（`project.md` 0章の表を参照）。`project.md` 3章の内容は繰り返さない。

## 書く層と書かない層
| 層 | 対象 | 方針 |
| :--- | :--- | :--- |
| 単体 | コアの純粋な計算（夢の解釈、ドグマの判定、1年分の環境変化など） | 計算・状態遷移の境界値に絞る |
| シミュレーション結合 | コアのループを通しで（夢の改ざん → ドグマ生成 → N年跳躍 → `WorldState`） | **最重要**。固定シードで、1ケースで大きく検証する |
| 手動（実機） | Godot 上の見た目・操作感・シーンの動作、コンパニオンとの接続 | テスト仕様書の手動テストに書き、自動化しない |

- 自動テストは `tests/TheogonyX.Core.Tests/`（xUnit）に置き、`src/TheogonyX.Core/` だけを対象にする。Godot を起動するテストは書かない。Godot 側で確かめたいロジックがあれば、コアへ移せないかを先に検討する。
- シミュレーションのテストは、乱数のシードとゲームデータを固定して実行する。テスト用のゲームデータは `tests/` の中に置き、`game/data/` の本番の値に依存させない（調整のたびにテストが壊れないようにする）。
- 型で表現できる制約を確かめるだけのテストは書かない。
- 似たテストケースを量産しない。

## 期待値
- `project.md` 3章の「実装と同じ計算で期待値を求めない」の例: `Assert.Equal(before - dogma.Intensity * rate * years, after)` ではなく、仕様書の受け入れ条件にある具体的な値（例: 「森林量 100 から 100年後に 70」）で書く。
- 浮動小数点の比較は、許容誤差を指定して比べる（例: `Assert.Equal(70.0f, state.ForestAmount, 0.001f)`）。
- 性質を確かめるテスト（同じシードなら2回実行しても同じ結果、森林量は0未満にならない、など）は上の制約の対象外。決定性のテストはシミュレーション結合の中で必ず1本持つ。

## テストデータ
- 入力値には、`docs/domain/glossary.md` の用語と、ゲーム内で実際に使われうる記号・値を使う（例: 記号は `SYM_RAIN`「雨」と `SYM_BLOOD`「血」）。`test`・`hoge`・`foo` のような意味の無い値は使わない。
- 境界値のテストでは、境界そのものの値（感情の極性の -1.0 / +1.0、年数 0、空の夢など）を使い、何の境界かをテスト名で分かるようにする。

## テスト仕様書とのつながり
- 自動テストには、対応するテスト仕様書のID（`TS-<機能名>-NNN`）を `[Trait("TS", "TS-<機能名>-NNN")]` で付ける。
