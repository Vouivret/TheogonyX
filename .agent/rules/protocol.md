# ホストとコンパニオンの通信のルール

> `.agent/rules/project.md` の下位ルール。矛盾した場合は `project.md` を優先する。
> 対象: PCホスト（Godot）とモバイルのコンパニオン（PWA）の間の WebSocket メッセージ（`project.md` 0章の表を参照）。

## 契約の原本
- メッセージの一覧（種類・向き・項目・型・バージョン）は `docs/protocol/messages.md` に表で書き、これを原本とする。C# のメッセージ型は `src/TheogonyX.Core/Protocol/` に置き、表と1対1で対応させる。
- コンパニオン（素の JavaScript。`js.md`）はビルドの工程を持たないため、型を生成しない。メッセージの `type`・`version`・項目、バイナリフレームの種別は `companion/js/protocol.js` の1か所に、定数と JSDoc の `@typedef` で書き、`docs/protocol/messages.md` の表と1対1で対応させる。表を変えたら、同じ変更で `protocol.js` も直す。
- メッセージの追加・変更を含む作業は、`docs/protocol/messages.md` の変更 → C# の型 → ホストの実装 → コンパニオンの実装、の順で進める。

## 互換性
- すべてのメッセージに `type` と `version` を持たせる。
- 項目の削除・意味の変更・型の変更は破壊的変更として扱い、`version` を上げる。項目の追加は、受け取る側が知らない項目を無視できる場合だけ互換とする。
- メッセージの形を変えるのは、依頼がそれを含む場合だけにする。片側の不具合を、メッセージの形を変えて解決しない（`project.md` 2.1）。

## 受け取ったメッセージの扱い（どのフェーズでも省略しない）
- コンパニオンから届くメッセージは外部入力である。型・範囲・存在しないID（記号・カード・NPCなど）を検証してからコアに渡し、検証に失敗したら捨てて `Warn` で記録する。
- ペアリング（接続時のトークン照合）を済ませていない接続からのメッセージは、コアに渡さない。
- WebSocket サーバーは、既定で同じLAN（プライベートアドレス）からの接続だけを受け付ける。待ち受けるアドレスやポートの既定値を変えるときは確認する。
- 受け取った値を、ファイルパス・シェルのコマンド・式の評価に使わない。

## 作業の進め方
- まず対象側（ホストかコンパニオン）のコードを読み、メッセージの整合性を確かめる必要があるときだけ反対側も読む。
