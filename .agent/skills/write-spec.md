# 仕様書・用語集を書く

> いつ使うか: `docs/domain/` の仕様書や用語集を新しく書くとき、更新するとき。仕様書の無い既存機能に手を入れる前に、現状を起こすとき。

## 入力
| 入力 | 例 | 必須 |
| :--- | :--- | :--- |
| 対象の機能 | 夢の解釈 | 必須 |
| 決まっているゲームのルール・受け入れ条件 | Issue、plan、人間からの説明 | 新規作成のとき必須 |

## 読むファイル
1. 対象の機能の仕様書（あれば）
2. `docs/domain/glossary.md`
3. 新規作成なら `docs/domain/_template.md`

## 手順
1. `docs/domain/<機能名>.md` を、無ければ `_template.md` をコピーして作る。1機能につき1ファイル。
2. 目的・ゲームのルール・受け入れ条件・対象外・未決を書く。次は書かずに、置き場所へリンクする。
   - 実装方法 → コード、`docs/architecture.md`
   - 設計判断の理由 → ADR
   - 通信メッセージの項目や型 → `docs/protocol/messages.md`
   - 画面のデザイン → ラフ・モック
   - 調整値の具体的な数値 → ゲームデータ定義（仕様書には決め方と範囲を書く）
3. 受け入れ条件は Given/When/Then の表で書き、IDを振る（`AC-<機能名>-NNN`）。IDは使い回さない。廃止した条件は行を消さず「廃止」と書く。
4. 状態を持つ機能は、状態遷移表を書く（行が現在の状態、列がきっかけ、マスが遷移先か「不可」）。すべてのマスを埋める。遷移の正は表であり、Mermaid の図は書く場合だけ表と一致させる。
5. 処理の順序・データの関係は、文章に加えて Mermaid の図（`sequenceDiagram`、`erDiagram` など）で書く。受け入れ条件は図にしない。
6. 先頭の `status` を決める。
   - 人間から受け取った仕様を書いた → `draft`（`approved` にするのは人間）
   - コードから現状を起こした → `as-is`
7. 用語は用語集に合わせる。新しい用語を使うときは、用語集への追加を提案する（コード上の名前・意味・各言語の表記・使わない言い方）。

## 既存のコードから現状を起こすとき（`as-is`）
- コードから読み取った挙動を書く。意図か不具合か判断できないものは「未決」に書く。
- ゲームのルールや受け入れ条件を、コードに無いものまで考え出さない。

## 出力
作成・更新した仕様書のパスと、`status`、「未決」に書いた項目の一覧を報告する。

## やってはいけないこと
- ゲームのルールや受け入れ条件を、人間から受け取っていないのに考え出す。
- 文章・図・表の食い違いを、どれかに合わせて黙って直す。確認する。
