# テスト仕様書を書く

> いつ使うか: `docs/test/` のテスト仕様書を新しく書くとき、更新するとき。

## 入力
| 入力 | 例 | 必須 |
| :--- | :--- | :--- |
| 対象の機能 | 夢の解釈 | 必須 |

## 読むファイル
1. 対象の機能の仕様書（`docs/domain/<機能名>.md`）
2. 対象の機能のテスト仕様書（あれば）。無ければ `docs/test/_template.md`

## 手順
1. **仕様書の受け入れ条件から作る。現在のコードの挙動から書き起こさない**（バグを期待結果として固定してしまうため）。仕様書が `status: as-is` なら、期待結果は確定させずに確認する。
2. `docs/test/<機能名>.md` を、無ければ `_template.md` をコピーして作る。1機能につき1ファイル。
3. 観点ごとに1行書く。
   - ID（`TS-<機能名>-NNN`）。使い回さない。廃止した観点は行を消さず、種別を「廃止」にする。
   - 確かめる受け入れ条件のID（`AC-<機能名>-NNN`）
   - 種別（自動 / 手動）と、自動ならテストの場所
4. 自動テストの手順や入力値の詳細は書かない（テストコードに書く）。手動テストは、手順と期待結果を書く。
5. 期待結果を変えるときは、既存テストの変更と同じ扱いにする（`project.md` 3章）。
6. 仕様書の受け入れ条件のうち、どの観点からも参照されていないものを報告する。

## 手動テストの実施記録
実施結果はテスト仕様書には書かず、`docs/test/results/YYYY-MM-DD-<版>.md` に追記する。

## 出力
作成・更新したテスト仕様書のパスと、観点の追加・変更・廃止の一覧、テストで確かめていない受け入れ条件を報告する。

## やってはいけないこと
- 仕様書に無い挙動について、期待結果を推測で書く。確認する。
