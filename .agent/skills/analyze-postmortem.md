# 障害の振り返りから再発防止のルールを提案する

> いつ使うか: `docs/postmortem/` に振り返りが追加されたとき、または人間に頼まれたとき。

## 入力
| 入力 | 例 | 必須 |
| :--- | :--- | :--- |
| 対象の振り返り | `docs/postmortem/2026-10-01-save-corruption.md` | 必須 |

## 読むファイル
1. 対象の振り返り
2. `.agent/rules/project.md`
3. 原因に関係する言語の `.agent/rules/<言語>.md`
4. 原因に関係する機能のテスト仕様書（`docs/test/<機能名>.md`）

## 手順
1. 振り返りの「原因」と「再発防止策」から、どの段階で防げたはずかを判断する。
   - AIが書いたコードで防げた → ルール（`.agent/rules/`）
   - 機械的に検出できた → CIのチェック
   - テストで検出できた → テスト仕様書の観点
   - 本番で早く気付けた → 監視（`docs/operations.md`）
2. 既存のルールやチェックで防げたはずなのに防げなかった場合は、新しく足すのではなく、既存のものの何が足りなかったかを書く。
3. 落とし込み先ごとに、具体的な変更案を差分の形で作る。

## 出力
ルールやテスト仕様書を直接書き換えず、次の形で提案する（`project.md` 8章）。採用するかどうかは人間が決め、PRで反映する。

```markdown
## 再発防止の提案: <振り返りのファイル名>

### どの段階で防げたか
<判断と理由>

### 変更案
| 落とし込み先 | ファイル | 変更内容 |
| :--- | :--- | :--- |
| ルール / CI / テスト観点 / 監視 | | |

### 差分
（ファイルごとの追加・変更の内容）

### 追加しない理由
<提案を見送った再発防止策があれば、その理由>
```

## やってはいけないこと
- 個人の注意力に頼る対策（「気を付ける」「よく確認する」）を提案しない。仕組みで防げる形にする。
- 1件の障害に対して、関係の薄いルールまで足さない。ルールは増えすぎると守られなくなる。
- 振り返りに書かれた個人名を、ルールや提案に書き写さない。
