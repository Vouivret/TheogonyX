# ADRを書く

> いつ使うか: plan で「ADR化」の印を付けた決定を記録するとき。ランタイムやフレームワークのメジャーバージョンを上げるとき。人間に頼まれたとき。

## 入力
| 入力 | 例 | 必須 |
| :--- | :--- | :--- |
| 記録する決定 | plan の決定事項の行 | 必須 |

## ADRにする決定
次のどれかに当たるもの。当たらない決定は plan や PR の説明に置いたままにする。
- 他のチケットやモジュールの実装方針を縛る
- 覆すと大きな手戻りになる
- 後から「なぜこうしたのか」と問われそうである

## 読むファイル
1. `docs/adr/0000-template.md`
2. 同じ `area` の、`status: accepted` のADR（覆す決定が無いかを確かめるため）

## 手順
1. `docs/adr/0000-template.md` をコピーし、`docs/adr/NNNN-<タイトル>.md`（既存の最大番号＋1）として作る。
2. メタデータ（`status: accepted`・`area`・`date`）を埋め、背景・決定・検討した他の案・結果を1ページに収めて書く。
3. 既存のADRを覆す場合は、古いADRの `status` を `superseded`、`superseded_by` を新しい番号にする。古いADRの本文は書き換えない。
4. `docs/architecture.md` の該当箇所から、新しいADRへリンクする。
5. 元の plan ファイルがあれば、そこからもリンクする。

## 出力
作成したADRのパスと、`superseded` にしたADRがあればその番号を報告する。ADRの追加は、PRで人間が承認する。

## やってはいけないこと
- 既存のADRの本文を書き換える。
- 検討していない「他の案」を、体裁のために作る。
